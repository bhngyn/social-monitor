§ Social Monitor

Team User Guide

Self-hosted social-media archiving and monitoring — what each surface does, where it falls back, and where the rules live.

What this is

Social Monitor ingests posts from Twitter, Instagram, Facebook, TikTok, and YouTube through Apify, captures full-page MHTML, screenshots, and original media, and surfaces them through a Next.js dashboard with alerting, topic sets, retention policies, and an audit log.

It runs as a docker-compose stack on a single host. The frontend lives at http://localhost:3000, the API at http://localhost:8000 (CORS-locked to :3000). Archived media lives on an external drive mounted as archive_data/; nothing on the page is served from a CDN.

Scope:

  • Archives public posts from configured sources and stores them durably.
  • Surfaces a review queue, full-text search, topic sets, and keyword alerts.
  • Does not log into private accounts, scrape behind paywalls, or post anywhere.
  • Does not moderate content — the operator decides what to do with each post.

Sidebar & layout

Every page sits inside a fixed dark-slate sidebar on the left and a light content pane on the right. The sidebar can be collapsed to icons with the chevron at the top.

  • Active item — current route is highlighted with a darker slate background. Dashboard matches only /; everything else matches by prefix, so /posts/abc still highlights "Posts".
  • "New" badge on Posts — a red pill with a count appears next to "Posts" when there are unreviewed posts in the recent 200-post sample. collapsed shows a red dot instead of the pill.
  • Collapse toggle — chevron in the header. Keyboard focus survives; tooltips appear on hover when collapsed.

Review queue (dashboard)

/ is the entry surface. It groups unreviewed posts by source so the operator can clear one account at a time rather than scroll a flat feed.

Source group

  • Header — platform name (colored text label, not an icon — see platform matrix), @username, and "· N new" count.
  • Preview list — up to three unreviewed posts, each showing a relative timestamp and a single line of text (clipped). Clicking a row opens the post detail page.
  • Review button (right side) — navigates to /posts?source_id=…, which pre-filters the posts page to just that source.

Affordances

  • Mark all reviewed (top right, only when there are groups) — sets every visible source to reviewed in one click. Stored client-side in localStorage; see limitations.
  • Recently captured — collapsible section showing the 10 most recent posts across all sources, regardless of review state. Toggle with the chevron.
  • Stats footer — four compact tiles: Total sources, Total posts, Posts today, Storage used. "Storage used" is the archive size reported by /api/storage/stats, formatted with formatBytes.

Empty states

  • No unreviewed posts — inbox icon with "No new posts" message. Recently-captured section still renders below.
  • No sources configured — same empty state applies; total counts stay at zero.

Sample window. The dashboard fetches the most recent 200 posts to compute groups and "new" counts. Older unreviewed posts still exist in the archive, but the dashboard won't surface them — use /posts with explicit filters to find them.

Posts robust

The browse-and-search surface. Left rail holds filters; main column holds either a feed of cards (default) or a 2–4 column thumbnail grid. Pagination is 20 per page.

Filter rail (240px, left)

  • Platform — five checkboxes (Twitter, Facebook, Instagram, YouTube, TikTok), multi-select. Changing any resets to page 1.
  • Date range — two HTML date inputs (from / to), both optional. Changing either resets to page 1.
  • Has media — single checkbox; filters to posts with attached image/video files.
  • Topic sets — list of all sets with the set's colored dot beside the name. Each is a multi-select checkbox.
  • Untagged — checkbox above the set list. When ticked it greys out the set list and filters to posts not in any set.
  • Source — searchable dropdown (SourcePicker component), multi-select.
  • "N filters applied" — small blue text appears when ≥ 1 filter is active.
  • Clear filters — only renders when ≥ 1 filter is active; resets all filters and pagination.

The search bar sits above the filter rail, in the main column. It submits on Enter or the Search button — typing alone does not debounce a query.

Feed view (card)

Each card carries, in order:

  • Checkbox (selection), platform label, @username, relative timestamp.
  • NEW badge — blue uppercase pill, shown when the post has not been reviewed.
  • Content-language chip — small uppercase tag (e.g. EN), shown only if the post's language differs from the current UI locale.
  • Up to three lines of text (clamped), then an optional image thumbnail (cover-fit, 160px tall).
  • Chip row, when non-empty: topic-set badges (in the set's color), notes count (pill button, opens an inline note panel), and small icons for mhtml_captured, screenshot_captured, hashes_computed — each is an icon-only marker with a tooltip.
  • Footer row: likes, shares (retweets/reposts), comments — counts only, no thumbs-up; and a PostCardActions menu on the right.

Grid view

2–4 column grid of thumbnails. If the post has no image, the cell shows a grey panel with the post text clipped to four lines. The card footer is reduced to just the source username. Clicking anywhere navigates to the post detail.

Selection & review banners

  • Unreviewed banner — appears above the list when any visible post is unreviewed: "N new" with a Mark all reviewed button on the right. Applies to the currently-filtered view only.
  • Selection banner — appears when ≥ 1 checkbox is ticked: "N selected" with an X to clear selection. The bulk-action surface itself (e.g. add-to-set) lives in PostCardActions per card; see the per-card menu, not this banner.

Keyboard shortcuts

Active only on /posts and only when the list has at least one post. The blue ring on a card marks keyboard focus.

  • j — focus next post (scrolls into view).
  • k — focus previous post.
  • Enter or o — open focused post detail in the same tab.
  • Shift+O — open the original post on its platform in a new tab (only if post_url is set).
  • x — toggle selection on the focused post.
  • s — mark the focused post's source as reviewed (drops the NEW badge from every post on that source).
  • Shift+? — open/close the shortcuts overlay.

The shortcut overlay lists more than is wired. The overlay shows t (tag) and n (note) entries, but the posts page does not currently bind them — pressing them does nothing. See known limitations.

Edge cases

  • Empty filter result — inbox icon with "No posts found / Adjust filters". Pagination disappears.
  • Loading — the page falls back to "Loading…" (the search-params Suspense fallback) before SWR resolves.
  • Search not submitted — typing in the search box does not query; you must press Enter or the Search button. Other filters apply on change.
  • Grid + no image — falls back to the text-only grey panel; thumbnails are never generated for video-only posts.

Post detail

/posts/[id]. Two-column layout: left panel is 60% wide and scrolls; right panel is 40% wide and sticky.

Left panel — top to bottom

  • Header card — platform label, source username, relative timestamp, and an external-link icon (only when post_url is set). Below it: the full post text with whitespace preserved.
  • Metadata grid — two-column grid of <dt>/<dd>: platform, platform post ID (monospace), posted timestamp, archived timestamp, and four yes/no rows for media downloaded, MHTML captured, screenshot, hashes computed.
  • Engagement — likes (heart), shares (repeat), comments (speech bubble), and views (eye, only when > 0). Below the icon row, every raw engagement key is dumped as small "label: value" pairs — useful when a platform returns custom fields.
  • Platform data — same flat key/value rendering, populated from post.platform_data. Only renders if the object is non-empty. Nested values are JSON-stringified inline.
  • Topic sets — colored pill per set, each linking to the set page. A dashed-border Add to set button opens a dropdown of all sets; clicking one adds the post immediately. "Not in any sets" when empty.
  • Notes — heading shows the count. There is an input plus Add button; submitting POSTs a new note. Existing notes are not rendered on this page — only the count and the add control. To see notes, use the inline notes panel from the post card on /posts.
  • Raw JSON — collapsible. When open, dumps JSON.stringify(post, null, 2) into a max-h-96 scroll container.

Right panel

  • Sticky media viewer — renders any attached media_files plus the MHTML and screenshot paths. When the post has no media and no captures, falls back to a card reading "No media files".

Edge cases

  • Loading — centered spinner.
  • Fetch error — heading plus the error message and a "Back to posts" link. Triggered if the ID is unknown or the API is unreachable.
  • Notes not displayed — by design on this surface; only the count is shown. The card-level inline notes panel renders them.

Sources robust

Each row is one account on one platform. Adding a source schedules it for polling by the Celery beat scheduler; the cadence is read from the DB row, not a cron file.

Table columns

  • Platform — colored text label.
  • User — avatar circle (first letter of username) + username, linked to /sources/[id].
  • Display name — optional; "—" if empty.
  • Posts — archived count from post_count.
  • Last polled — relative time, or "never".
  • Active — switch-style toggle. Green when on, slate when off. Click toggles immediately; no confirmation.
  • Actions — pencil (edit) and trash (delete).

Add / Edit modal

  • Fields: platform (select, required), username (text, required), profile URL (URL, optional), poll interval in seconds (number, min 60, default 3600).
  • platform_id defaults to the username if left blank.
  • Errors render in a red box at the top of the form. Save button shows a spinner while saving.
  • X in the header closes without saving.

Edge cases

  • Delete — browser confirm() with the localized confirmation text. Cancel aborts; OK fires the DELETE.
  • Toggle failure — falls back to a browser alert() with the localized error and leaves the row in its current state until the SWR refresh.
  • Inactive source — the beat scheduler skips it on its next pass; no posts are deleted.

Topic sets robust

Labels with colors used to group posts across sources. A post can belong to many sets; the set color is reused on post cards and detail-page chips.

  • Grid — responsive 1–3 column grid of cards. Each card shows a colored dot, name, optional description (2-line clamp), and a post count.
  • New set — opens an inline form above the grid: name (required), description (textarea, optional), color (HTML color picker, default #3B82F6).
  • Delete — trash icon on the card, confirmed via browser confirm(). Posts are not deleted — only set membership.
  • Empty state — folder icon, "No topic sets yet", with a hint.

Create errors fail silently. If the create POST returns non-OK, the form does not surface an error — the page just doesn't refresh. Check the browser console or the API logs if a new set doesn't appear.

Alerts best-effort

Keyword patterns matched against post text. Each alert is one regex and one delivery channel — browser notifications or a webhook POST.

Alert row

  • Active toggle — switch-style, blue when on, grey when off. Click toggles immediately.
  • Name — operator-chosen label.
  • Pattern — shown in a monospace inline-code background. Supports regex; the placeholder hints at alternation (elecciones|votación).
  • Notify via — browser or webhook.
  • Event count — number of times this alert has fired since creation.
  • Delete — trash icon, confirmed via confirm().

Create form

  • Name (required), keyword pattern (required), notify via (browser or webhook), webhook URL (only when notify via = webhook, then required for delivery).
  • Help text under the pattern field: "supports regex".

Pattern errors are not validated client-side. An invalid regex is saved as-is; whether it ever matches depends on the worker's matcher. Test patterns on a few archived posts before relying on them.

Timeline

Chronological view of posts, grouped by post date. Useful for visual scanning across sources. Always limited to the most recent 200 posts that match the filters.

  • Filters (top row) — date from, date to, single platform select (all / twitter / instagram / facebook / tiktok / youtube). All apply on change; no submit button.
  • Vertical rail — thin grey line on the left. Each date group is anchored by a small date badge on the rail.
  • Card — platform color dot, platform name, @username, post time (HH:MM), optional "N media" count, and a 2-line text preview. Links to the post detail.
  • Unknown date — posts with no post_timestamp are grouped under "Unknown date".
  • Empty state — clock icon, "No posts to show / Adjust filters".
  • Error state — renders the error message in red at the top of the content area.

Ingestion runs

Every poll cycle is one row. Runs are recorded by the worker and update in place as they progress. The page polls a static list — it does not stream — so a long-running job will sit at "running" until you press Refresh or reload.

Columns

  • Status — colored pill. pending, running, completed, failed, partial.
  • Trigger — how this run was started (scheduled, manual, etc.).
  • Found — total posts the run saw on the platform.
  • New — posts that were not already in the archive and got inserted.
  • Duration — completed_at − started_at, formatted as ms / s / m. "—" until both are set.
  • Started — local datetime, or "—" if not started.
  • Errors — red count when errors[] is non-empty, grey "—" otherwise. The error rows themselves are not surfaced on this page; they live in the ingestion_runs.errors JSONB column.

Affordances

  • Refresh (icon button) — re-fetches the table.
  • Trigger all — POSTs /api/ingest/trigger with an empty body; refetches after a 1-second delay. Disabled briefly while the request is in flight.

Audit log robust

Append-only record of every meaningful event in the ingest pipeline: a post being seen for the first time, a media file being downloaded, an MHTML or screenshot being captured, content hashes being computed, an ingestion run completing, and media download errors.

  • Filter (top) — single select for event type, plus a total-event count text.
  • Row — colored event-type pill, entity type (post, media, etc.), the first 8 chars of the entity UUID in monospace, then a local datetime, right-aligned.
  • Pagination — 50 per page. Previous/Next appear only when total > 50.
  • Empty state — shield icon, "No audit events", with a hint.

Event types and colors

  • post_first_seen, ingestion_completed — green.
  • media_downloaded — blue.
  • mhtml_captured — purple.
  • screenshot_captured — indigo.
  • hashes_computed — teal.
  • media_download_error — red.

Unknown event types fall back to grey. The page does not show the event's details JSON — query the API or the DB if you need the payload.

Storage & retention manual

/settings/storage. Reads /api/storage/stats and /api/storage/retention-policies. The disk numbers come from shutil.disk_usage against the archive root, so they reflect the whole mount, not just Social Monitor's footprint.

Drive overview (four tiles)

  • Drive total — total bytes of the mount.
  • Used — used bytes plus a blue progress bar and a percentage line. Reflects everything on the disk, not just the archive.
  • Free space — remaining bytes.
  • Archive size — sum of media + capture bytes attributable to Social Monitor (archive_bytes).

Breakdowns

  • By platform — bytes per platform (twitter, instagram, …). Platforms with no archived bytes are omitted.
  • By media type — bytes per media type (image, video, …). Same omission rule.

Both panels show "No data yet" when their map is empty.

Retention policies

  • Row — name, target type (global / platform / source), action (delete_media / delete_all / compress), and "N days" when max_age_days is set. Trash icon on the right deletes (with confirm()).
  • Add policy — inline form: name, scope, max age days (optional), action.

Defining a policy is not the same as enforcing one. The UI lets you create and delete policies. Whether and how they fire is the worker's responsibility — check ingestion logs and the audit log to confirm the corresponding deletes/compressions actually ran. Treat policies as declarations, not guarantees, until you see the audit trail.

Platform support matrix

Five platforms are wired into the ingest pipeline through Apify. Each has a normalizer under backend/app/services/normalizers/ that maps the Apify payload into the unified Post shape.

Note that platform "icons" in the UI are colored text labels, not glyphs — platformIcon("instagram") returns the string "Instagram", which is rendered in pink. There are no SVG brand icons.

Platform Ingest Capture path What to double-check
robust
Twitter / X		 Apify scraper → twitter normalizer MHTML & screenshot via Playwright; media via yt-dlp where applicable Posts behind login gates may return empty text_content; check the platform_data dump on the detail page.
robust
Instagram		 Apify scraper → instagram normalizer MHTML & screenshot; media via yt-dlp Stories and reels return different payload shapes — see docs/apify-output-schemas.md for the field map.
best-effort
Facebook		 Apify scraper → facebook normalizer MHTML & screenshot; media as available Facebook surfaces vary a lot between page / group / profile; expect occasional missing engagement counts.
robust
TikTok		 Apify scraper → tiktok normalizer MHTML & screenshot; video via yt-dlp on worker-media Very large videos may hit MAX_VIDEO_FILESIZE / MAX_VIDEO_DURATION / MAX_VIDEO_RESOLUTION caps and skip the media-download step.
robust
YouTube		 Apify scraper → youtube normalizer MHTML & screenshot; video via yt-dlp on worker-media Same video caps apply. Live streams and unlisted videos are not guaranteed.

Adding a sixth platform means adding a normalizer under backend/app/services/normalizers/ and wiring it into the ingest task — there is no UI to register a new platform string.

Reliability & background machinery

These run quietly. List them so you can recognise the fingerprints when something looks off.

  • Three Celery queues, on purpose. worker-default (concurrency 4) runs alerts, link expansion, profile snapshots, retention, and hashing. worker-media (concurrency 2) runs yt-dlp and ffmpeg. worker-capture (concurrency 1) runs Playwright MHTML and screenshot capture — single-concurrency so chromium instances don't pile up.
  • DatabaseScheduler reads poll cadence from the DB. The custom beat scheduler in backend/app/worker/scheduler.py reads each source's poll_interval column. To change a source's cadence, update the row through the Sources page — there is no cron file to edit.
  • Health endpoint. GET /health on the API returns {status, checks: {database, storage}}. The storage check runs shutil.disk_usage against the archive root and reports total / free GB plus used percent. Use it to confirm both the DB connection and the archive mount.
  • Audit log as receipt. Every capture, download, and hash computation writes a row. If you're not sure whether a job ran, filter /audit on the matching event type rather than guessing from the post-detail flags.
  • Review state lives in localStorage. The "NEW" badge and the dashboard groups are computed against localStorage in the browser, keyed by source. There is no server-side notion of "reviewed." Different browsers / private windows / cleared storage will see different review states.
  • File hashes for dedupe. FileHash rows let the system recognise the same media across posts. Hash computation is asynchronous; the hashes_computed flag on a post becomes true only after the worker finishes.
  • CORS lockdown. The API allows requests only from http://localhost:3000. Reaching the API from another host requires editing backend/app/main.py.

Known limitations

  • Review state is per-browser. Marking posts reviewed in one browser does not propagate to another. Clearing site data resets the queue.
  • Dashboard groups only the most recent 200 posts. Older unreviewed posts exist in the archive but won't appear on / — they're only reachable through filters on /posts.
  • Shortcut overlay over-promises. The overlay shows t (tag) and n (note) but neither is bound on the posts page. They are wired in the overlay component for future use, not active.
  • Topic-set creation fails silently. The create POST has no error surfacing; a failed save just doesn't appear in the grid. Same for the alerts create form on certain errors.
  • Runs page does not stream. Long-running runs sit at running until you press Refresh. There is no SSE or websocket — the page is request/response only.
  • Audit details JSON is not visible in the UI. The row shows event type + entity type + first-8 UUID + timestamp, but not the details JSONB payload. Query the API or DB directly when you need the payload.
  • Retention policies declare, the worker enforces. Creating a policy does not delete anything immediately. Watch the audit log to confirm the enforcement job ran.
  • Disk full is silent in the UI. If the archive mount fills, captures will start failing — the failures show up in the audit log and the worker logs, not on the dashboard. Watch the drive overview tile.
  • No tests. The repo has no test suite — verifying changes means running against a real Apify token and watching the audit log.

Where the rules live

The files and tables that actually drive runtime behaviour:

  • .env — every external-facing setting. Apify token, archive host path, Postgres credentials, Redis URL, media caps (MAX_VIDEO_FILESIZE, MAX_VIDEO_DURATION, MAX_VIDEO_RESOLUTION), poll defaults, per-service CPU and memory limits. See .env.example for the full list.
  • docker-compose.yml — the seven services (db, redis, api, worker-default, worker-media, worker-capture, beat, web) and their resource limits. To change concurrency, edit the worker service entry.
  • backend/app/main.py — FastAPI app + CORS list. The CORS origins are hard-coded to http://localhost:3000; widen before exposing the API.
  • backend/app/worker/scheduler.py — the custom DatabaseScheduler. Reads poll intervals from the sources table; no cron file involved.
  • backend/app/worker/tasks/ — one module per task type (ingest, apify_fetch, capture, media_download, link_expansion, hashing, profile_snapshot, retention, alerts). Each is routed to the appropriate queue.
  • backend/app/services/normalizers/ — one normalizer per platform. Adding a platform = adding a normalizer here plus the platform string in the API and frontend.
  • backend/alembic/versions/001_initial_schema.py — the single baseline migration. Schema changes go in new alembic revisions, not by editing the baseline.
  • docs/apify-output-schemas.md — the platform-specific Apify response shapes the normalizers are written against.
  • sources table — per-source poll cadence and active flag. Edit through the Sources page; the scheduler picks up changes on its next loop.

Restart impact: changes to .env or docker-compose.yml need make stop && make start. Schema changes need make migrate. Source poll intervals are picked up live by the next beat tick — no restart.
